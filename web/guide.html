MAGNETS shared queue

API guide

How to push spectroscopic targets into the shared MAGNETS observing queue and read the schedule back — for both automated pipelines (bearer key) and people (browser login). The queue ranks every group’s targets together and the scheduler turns them into per-instrument observing plans (LLAMAS and LDSS3 are two parallel systems). Everyone can see the whole queue; you can only edit your own program’s targets.

Getting started (30 seconds)

  1. Log in — open the dashboard and sign in with your program + password (from the queue admin). Scripts/pipelines use a bearer API key instead (see Authentication).
  2. See the shared queue — everyone's targets, split by instrument (LLAMAS / LDSS3) and ranked by priority. You can edit only your own program's rows.
  3. Add a target — the add-form (or POST /v1/targets): a name or RA+Dec, a priority (1 = highest … 5 = lowest; P0 = must-observe), instrument, and an anticipated mag.
  4. Read tonight's plan — the observing plan shows what fits, each target's observable window, and downloadable exports (catalog / CSV / print sheet).

That's it. The rest of this page is the full reference.

Base URL

https://magnets-collab.onrender.com

Authentication

Two interchangeable ways to authenticate; both resolve to your program. Reads accept either; writes are scoped to your own program.

1. Bearer API key (pipelines / scripts)

curl -H "Authorization: Bearer <YOUR_KEY>" \
     https://magnets-collab.onrender.com/v1/queue

Your program’s key is issued by the queue admin. Keep it secret.

2. Browser login (people)

Sign in on the dashboard with your program + password; the session cookie then authorizes the same endpoints from the browser.

Quickstart — submit a target

POST /v1/targets takes a JSON array (submit one or many). The program is inferred from your key — do not send it in the body.

curl -X POST https://magnets-collab.onrender.com/v1/targets \
     -H "Authorization: Bearer <YOUR_KEY>" \
     -H "Content-Type: application/json" \
     -d '[{"name":"SN2026abc","ra":331.93,"dec":-7.50,
           "priority":"P1","instrument":"LLAMAS","mag":19.2}]'

Response is a per-item result array (one bad target never fails the batch):

[{"status":"ok","id":42,"updated":false,
  "canonical_ra":331.93,"canonical_dec":-7.5,
  "resolved_from":"coords","shared_with":[]}]

The target object

fieldtypenotes
namestringTarget name / resolvable identifier. Optional if you send ra+dec.
ra, decfloat (deg)J2000 degrees. Provide these or a resolvable name.
priority reqenumP0 | P1 … P5 — see tiers below.
instrumentenumLLAMAS | LDSS3 | EITHER. Default LLAMAS.
magfloatAnticipated r-band mag. Required for a coords-only new source (used to size the exposure).
redshiftfloatOptional; improves the exposure estimate.
exposure_minutesfloatOptional; overrides the estimate.
bandstringOptional; band of the quoted mag.
notesstringOptional free text (classifier, provenance, caveats).

Dedup / upsert: a submission within 2″ of an existing target of the same program updates it (priority, mag, …) rather than duplicating — re-submit the same object freely as it evolves.

Priority tiers

tiermeaning
P0Observe-tonight guarantee. A mandatory reservation — use sparingly (ToO / must-not-miss).
P1 … P5Ordinary priority within your program, on the shared 1–5 scale (P1 highest, P5 lowest; P4–P5 are low/opportunistic — e.g. fillers for otherwise-idle sky). This is your delegated authority: your P1 outranks your P2, and we never re-sort your internal order. Cross-program fairness is handled by budget availability, not by re-ranking your list.

Instruments

LLAMAS (IFU, ~1-min overhead) and LDSS3 (slit, ~10-min overhead) are scheduled as parallel systems with separate budgets. EITHER lets the scheduler place a target on whichever instrument fits. Pick the instrument that matches the night.

Python example

import requests

BASE = "https://magnets-collab.onrender.com"
KEY  = "<YOUR_KEY>"
h = {"Authorization": f"Bearer {KEY}"}

# submit a batch
targets = [
    {"name": "SN2026abc", "ra": 331.93, "dec": -7.50,
     "priority": "P1", "instrument": "LLAMAS", "mag": 19.2,
     "notes": "Ia, z=0.05, near peak"},
]
r = requests.post(f"{BASE}/v1/targets", json=targets, headers=h)
for item in r.json():
    print(item["status"], item.get("id"), item.get("error", ""))

# read the shared queue
print(requests.get(f"{BASE}/v1/queue", headers=h).json())

# download tonight's LLAMAS catalog
cat = requests.get(f"{BASE}/v1/plan/export",
                   params={"date": "2026-08-10", "instrument": "LLAMAS", "fmt": "catalog"},
                   headers=h).text
print(cat)

How the queue treats your targets

  • Ranked together, order preserved. Your within-program priority is respected; the scheduler decides cross-program placement by observability + budget availability, not by re-ranking your list.
  • Charged on observation. Time is docked from your program budget when a target is actually observed (parity queue — no tokens).
  • Static plan. Nights are planned ahead of time; the observer adapts live. The plan shows each target’s observable window, not a fixed clock slot.
